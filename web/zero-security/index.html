Full antivirus programme · working foundation preview

Security that explains itself.

Zero Security is being engineered as a proper local-first Windows antivirus, built on the open ZSEC Shield foundation. The working preview checks selected files on demand, verifies signed data-only rules and automatically encrypts recoverable quarantine objects.

Signed data, never commands

Rule feeds can describe exact detection data. They cannot request execution, deletion or system changes.

Recoverable by design

The project retains recovery objects, refuses overwrite restore and treats incomplete operations as incomplete.

Automatic protection model

Automatic where it should be. Explicit where it matters.

Routine cryptographic key handling is designed to happen without password prompts. The preview keeps file selection, quarantine enablement and restore visible because automation should not hide consequential actions.

Choose a scope

Select the file or directory you want checked. The scanner does not silently sweep unrelated storage.

Check deterministically

SHA-256, exact-byte rules and verified signed feed data produce explainable configured matches.

Protect a match

When quarantine is enabled, the implementation authenticates metadata and encrypts the recovery object before source removal.

Review or restore

Entries remain inspectable. Restore refuses unsafe paths and never overwrites an existing destination.

i

No hidden deletion

The current preview has no purge command. If the original cannot be removed safely, the operation is reported as incomplete rather than presented as successful quarantine.

Authenticated quarantine

Established cryptography. No invented shortcuts.

The encrypted-quarantine work is implementation-preview code and remains release-gated. Its security properties come from established primitives, key management and testing.

01

Automatic device root

A random device key is created once. On Windows, the design seals it with CurrentUser DPAPI before it is written to disk.

02

Fresh key per entry

Each quarantined object receives a new random AES-256 content key instead of reusing one raw encryption key for every file.

03

Metadata bound to bytes

AES-256-GCM authenticates file bytes together with canonical identity, path, hash, size and lifecycle metadata as additional data.

04

Verify before publish

Restore reconstructs and authenticates the same metadata before any plaintext is made available at its destination.

05

ZBA provenance

Zero Boundary Algebra records typed quarantine, verification and recovery transitions. It is an audit vocabulary, not a substitute for cryptography.

06

Recovery remains separate

A future recovery kit will wrap a recovery key without exposing the raw device root. Lost-key and revocation drills are required before release.

Fail-closed architecture

Small components. Narrow authority.

The product architecture separates the interface, privileged broker and hostile-file parsing. The current public foundation is a user-run CLI; service and worker layers are future release gates, not claimed capabilities.

  • The currently registered antivirus remains active during preview development.
  • Feeds contain data, not remote commands.
  • Untrusted parsing belongs in bounded workers.
  • Invalid signatures, rollback records or schemas fail closed.
  • Updates need expiry, rollback and freeze protection.

Evidence before claims

Know exactly what is available.

A passing test proves a defined path works. It does not establish real-world malware-detection efficacy. Zero Security separates shipped foundations, implementation work and future plans.

Public foundation

Deterministic on-demand SHA-256 and exact-byte checks, signed data-only feed verification, structured reports and recoverable quarantine in ZSEC Shield.

Implementation preview

Automatic AES-256-GCM quarantine protection, operating-system key sealing and authenticated ZBA lifecycle records under active test and release review.

Designed, not shipped

Optional YubiKey/passkey recovery, restricted Windows broker, bounded parser workers and licensed-engine adapters.

Not claimed

Real-time protection, memory scanning, EDR, complete antivirus coverage, zero-day prevention, a clean system verdict or guaranteed protection from attackers.

Privacy contract

Your files stay local by default.

File hashing, configured rule matching and quarantine processing happen on the device. The preview has no automatic sample upload, advertising identifier, account requirement or remote-control channel.

Local-first does not mean pretending a connected product never uses a network. Update checks may disclose only the documented product, version, platform, architecture, channel and coarse rollout cohort.

A future sample upload must ask first

  • Separate opt-in for each selected item.
  • Visible purpose and destination.
  • Retention, region and sharing terms before transmission.
  • No filenames, local paths or file contents in routine diagnostics.
  • Crash reporting remains a separate opt-in.

Optional recovery factor

YubiKey support—designed carefully, not advertised early.

The planned consumer flow prefers a compatible FIDO2/WebAuthn authenticator with verified PRF support. It wraps a recovery key after physical presence and local verification; it never stores a reusable YubiKey PIN and does not interrupt every routine scan.

Status: designed, not shipped. Capability detection, lost-key drills, revocation tests and non-destructive recovery self-tests remain required gates.

Open-core, clearly labelled

Auditable where trust is earned. Private where secrets must stay private.

Open source means source can be viewed and modified under its licence. Zero Security does not call hidden code “open source,” and it does not treat compilation, minification or obfuscation as a security boundary.

Public and auditable

  • ZSEC Shield deterministic scanner.
  • Signed data-only feed format and verifier.
  • Encrypted quarantine format and ZBA records.
  • Threat models, privacy contracts and test fixtures.
  • Reproducible packaging and update specifications.

Separately licensed or private

  • Third-party OEM engines and proprietary signatures.
  • Production signing keys, HSM policy and release credentials.
  • Optional managed reputation, sync and fleet services.
  • Customer-support systems and private operational data.
  • Future Windows components until their release model is ready.

Questions, answered plainly

Zero Security FAQ

Does Zero Security replace Microsoft Defender or Malwarebytes?

Not yet. Zero Security is being built as a genuine primary Windows antivirus, but the current public build is an on-demand implementation preview. Keep the antivirus currently registered with Windows active until Zero Security passes real-time integration, signing, compatibility, efficacy, Microsoft onboarding and transactional cutover gates.

Does Zero Security upload my files?

Not by default. File hashing, configured rule matching and quarantine processing occur locally. Any future sample upload must be a separate per-item choice that identifies its destination, purpose, retention and sharing terms before transmission.

Is quarantine encryption automatic?

The release-gated implementation is designed to create and protect keys automatically after an operator explicitly enables quarantine for a scan. Selecting a scan scope, enabling quarantine and restoring an item remain visible choices.

What does ZBA do in Zero Security?

Zero Boundary Algebra supplies typed lifecycle and provenance records for events such as quarantine, verification and recovery. Cryptographic security comes from established authenticated encryption, signatures and operating-system key protection—not from ZBA labels alone.

Can I use a YubiKey for recovery?

YubiKey and passkey recovery is designed but not shipped in the preview. The intended flow uses an optional compatible authenticator to help unwrap a recovery key after physical presence and local verification. Routine scanning should not require a YubiKey touch.

Is every Zero Security component open source?

No. Zero Security follows an open-core model. The scanner, data-only feed verifier, quarantine format, ZBA records, browser rules and public specifications are intended to remain auditable. Optional OEM engines, signing infrastructure and managed services may be separately licensed and are labelled as such.
